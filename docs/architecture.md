# Архитектура

Проект организован по функциям и разделён на слои:

```text
lib/
  app/                    конфигурация приложения и маршруты
  core/                   тема, форматирование и общие виджеты
  features/
    accounts/               локальное демо аккаунтов, модели и импорт гостя
    home/presentation/
    inventory/
      application/        контроллер сценариев
      data/               локальное хранилище и каталог
      domain/             состояние приложения
      presentation/       экраны и компоненты
    medicines/domain/     модель препарата
    reminders/            расписание и журнал приёма
    scanner/              сканирование и разбор GTIN
    settings/
    shell/                адаптивная навигация
```

## Поток данных

```text
Экран → AppController → MedicineRepository → SharedPreferences
                  ↓
           неизменяемый AppState (аптечки → упаковки → события приёма)
```

`MedicineRepository` является интерфейсом. Сейчас состояние прототипа хранится локально в JSON через SharedPreferences. Локальные демо-профили разделены ключами SharedPreferences. `activeProfileIdProvider` определяет область репозитория; гостевой ключ сохранён для миграции. При смене профиля контроллер перестраивает состояние. Реальной серверной синхронизации нет.

`DrugCatalogService` также отделён интерфейсом. `drugCatalogServiceProvider` объединяет поиск по части названия/МНН и поиск по GTIN для сканера. По умолчанию подключён `MdlpDrugCatalogService` с полной открытой выгрузкой МДЛП в assets. Публичный справочник кешируется, поиск не отправляет пользовательские запросы издателю. Поиск в форме выполняется с debounce, защитой от устаревших ответов и ручным режимом; вариант подставляет только характеристики препарата. Для последующей доставки обновлений можно реализовать собственный API с тем же интерфейсом. Текущая версия обновляется импортёром и новой сборкой. Подробности — в [drug-catalog.md](drug-catalog.md).

## Границы прототипа

Реализовано:

- локальный учёт нескольких аптечек и отдельных физических упаковок;
- группировку одинаковых препаратов и фильтрацию внутри выбранной аптечки;
- вычисление статуса общего срока и срока после вскрытия, включая состояние нехватки данных;
- Data Matrix/EAN-сканер и выделение GTIN;
- ручное добавление с поиском и автозаполнением по полной открытой выгрузке МДЛП;
- расписание и журнал факта приёма;
- адаптивный интерфейс и тёмная тема.

Следующими отдельными модулями подключаются:

- системные локальные уведомления;
- серверная доставка обновлений справочника МДЛП;
- SQLite/Drift для больших объёмов;
- подключение настоящей авторизации, облачная синхронизация и семейный доступ;
- OCR срока годности.

## Основа аккаунтов

`features/accounts` содержит локальный контроллер демо, экран входа/привязки, описание приватности и идемпотентный импорт гостя. Эти данные не подтверждают личность. Сохранение профиля выполняется до публикации состояния; сохранение аптечки проверяет текущую область и не публикует устаревший профиль.

`server/auth.py` — независимое dev-ядро подтверждения email, Яндекс PKCE, привязки идентификаторов, сеансов и удаления. `server/app.py` — loopback HTTP-адаптер. В SQLite сервера нет лекарств и истории; медицинские маршруты закрыты. PostgreSQL-проект в `server/migrations/001_accounts.sql` предназначен для последующей реализации. Flutter и API сейчас не связаны. Полная модель и ограничения описаны в [accounts.md](accounts.md).
