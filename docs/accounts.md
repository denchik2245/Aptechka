# Аккаунты и привязка аптечек

Проектное решение от 1 октября 2026 года. Реализован локальный Flutter-сценарий и отдельная исполняемая серверная основа. Публичного сервиса, действующих юридических документов и облачной синхронизации пока нет.

## Что работает сейчас

Экран «Аккаунт» открывается с главной страницы и из настроек. Можно пройти демо входа через Яндекс или почту, привязать второй способ, изменить имя, выйти и удалить профиль с его локальными записями. Последний способ входа отключить нельзя. Адреса демо ограничены `example.test`; показанный код `123456` служит исключительно проверке интерфейса. Яндекс использует вымышленную Анну и не открывает реальную авторизацию.

Каждый профиль получает UUID и своё локальное хранилище. Гость сохраняет прежний ключ, поэтому обновление приложения сохраняет существующие записи. Новый профиль начинается с пустой личной аптечки. Пользователь выбирает гостевые аптечки для копирования; связанные упаковки, расписания и история переносятся вместе. Оригиналы остаются у гостя. Детерминированные идентификаторы исключают повторные копии; уже импортированные записи не перезаписываются. Демонстрационная общая аптечка по умолчанию не выбрана. Нередактируемую аптечку импортировать нельзя.

Настройки и резервная копия относятся к текущему профилю. Восстановление назначает владельцем текущий профиль и не переключает аккаунт. Поиск и фильтры сбрасываются при смене профиля. Позднее завершившаяся запись не может опубликовать состояние другого профиля. SharedPreferences предназначен для прототипа: изоляция ключей не заменяет защиту хранилища на устройстве и серверную авторизацию.

Flutter пока не обращается к API: профили интерфейса и серверные аккаунты независимы. Это позволяет безопасно проверить продукт без настоящих учётных данных и передачи сведений о лекарствах.

## Способы входа

| Способ | Российский выпуск | Подготовлено / следующий шаг |
| --- | --- | --- |
| Почта и одноразовый код | Основной резервный способ через собственную систему российского оператора | Демо UI, серверная выдача и проверка кода; SMTP через проверенного подрядчика в РФ |
| Яндекс ID | Основной внешний способ после проверки условий и регистрации приложения | Демо UI, серверный Authorization Code + PKCE S256; нужны client ID, secret, redirect URI |
| VK ID | Дополнительный способ после оценки спроса | Пока отключён; отдельно реализовать и проверить официальный протокол |
| Google | Отключён в российской конфигурации | Возможен отдельный зарубежный выпуск после проверки применимых требований |
| Apple | Отдельное решение для iOS | Согласовать правила App Store 4.8, российское регулирование и состав способов входа |
| Телефон, ЕСИА | Возможное расширение | Не требуются для обычного домашнего учёта; затраты и сбор дополнительных данных пока не оправданы |

У аккаунта собственный UUID, у способа входа — уникальная пара `(provider, subject)`. Email Яндекса не является идентификатором аккаунта. Совпадение почты у разных провайдеров не объединяет аккаунты. Привязка выполняется из уже открытого аккаунта после свежего подтверждения входа и отдельного подтверждения нового провайдера. Если способ занят другим аккаунтом, операция отклоняется. Замена почты требует подтверждения нового адреса; перенос данных между двумя существующими аккаунтами — отдельный будущий сценарий с доказательством владения обоими.

При потере доступа предлагается второй ранее привязанный способ. Поддержка не меняет владельца по имени, списку лекарств или скриншоту. До отдельной безопасной процедуры восстановления нельзя обещать восстановление аккаунта с единственным потерянным способом. После входа предлагаем привязать резервный способ, но не заставляем вводить телефон.

## Первый вход и привязка

1. Пользователь выбирает способ и видит, какие данные требуются для аккаунта.
2. Сервер подтверждает почту или проверяет ответ провайдера, создаёт аккаунт либо находит его по подтверждённому идентификатору.
3. Аптечки на устройстве остаются локальными до явного выбора пользователя. При включении облака отдельный экран показывает перечень данных, основание обработки и документы.
4. После выполнения юридических и инфраструктурных условий пользователь выбирает аптечки; сервер атомарно создаёт их с новым владельцем, сохраняя таблицу соответствия локальных ID и ключ идемпотентности.
5. До подтверждённого сервером завершения локальные оригиналы не удаляются. При ошибке можно повторить запрос и продолжить гостевой режим.

В настоящем клиенте системный браузер открывает провайдера; пароль вводится только у него. Секрет приложения хранится на сервере. Для мобильного callback нужен проверенный app/universal link и одноразовый короткоживущий билет обмена; токены нельзя передавать в URL или хранить в SharedPreferences. Мобильная сессия хранится в Keychain/Keystore, веб-сессия — в Secure HttpOnly cookie.

## Владение, совместный доступ и приватность

Аптечка принадлежит аккаунту; записи упаковок связаны с аптечкой, а личное расписание и история — с аккаунтом. Наличие доступа к аптечке не раскрывает автоматически личную историю приёма. Дети и профили подопечных не включаются в первый публичный выпуск до определения основания и правил представительства.

| Действие | Владелец | Редактор | Наблюдатель |
| --- | --- | --- | --- |
| Просмотр общих упаковок | Да | Да | Да |
| Изменение упаковок | Да | Да | Нет |
| Приглашение и отзыв участников | Да | Нет | Нет |
| Передача владения / удаление аптечки | Да, с повторным входом | Нет | Нет |
| Чужое личное расписание и история | Нет по умолчанию | Нет | Нет |

Приглашение — одноразовый случайный токен, в БД его хеш, срок действия 48 часов. Оно привязано к конкретной аптечке и роли, отзывается владельцем и требует аутентифицированного принятия. Для адресного приглашения дополнительно проверяется подтверждённый адрес получателя. Ссылка не даёт доступа до принятия. Перед приглашением показывается состав открываемых данных; основания обработки данных другого человека проверяются отдельно. Для каждой операции сервер сам проверяет членство и роль; `canEdit` клиента не является доказательством доступа.

Удаление владельца: сначала передать общую аптечку согласившемуся участнику или явно удалить её для всех с повторным подтверждением. Для участника удаляется членство, общая аптечка остаётся. Отзыв доступа блокирует новые запросы немедленно; следующая синхронизация очищает локальную копию. Уже выгруженные участником файлы нельзя гарантированно отозвать — это показывается до предоставления доступа.

## Синхронизация и работа без сети

Будущая модель: российский API + PostgreSQL, локальная SQLite/Drift, очередь операций с UUID, `revision` и ключом идемпотентности. Сервер выводит `account_id` из сессии и проверяет роль; произвольный ID из тела запроса не меняет владельца. Новое устройство скачивает только разрешённые аптечки и собственные личные записи. Создание, принятие приглашения и миграция гостя выполняются транзакционно.

Изменение передаёт ожидаемую ревизию; при конфликте сервер возвращает 409 с актуальной записью. Количество, даты срока и история не перезаписываются молча: пользователь выбирает версию или повторяет изменение. Удаления представлены tombstone до обработки устройствами. Факты приёма получают уникальный идентификатор события и не дублируются при повторной отправке. После выхода очередь и база прежнего аккаунта закрываются; политика сохранения локальной копии выбирается явно. На общем устройстве доступ к оставленной базе потребует отдельной локальной блокировки.

`server/migrations/001_accounts.sql` — проект PostgreSQL-модели, а не подключённая миграция рабочего API. Маршруты синхронизации в текущем API возвращают 423, включая попытку передать клиентский флаг согласия.

## Настройки аккаунта в онлайн-версии

Приоритет P0: имя, подтверждённые способы входа, добавление резервного способа, устройства и завершение сеансов, состояние синхронизации и повтор ошибок, импорт гостевых записей, экспорт, отзыв согласия, выход, удаление аккаунта. Раздел общего доступа: участники, роли, приглашения и передача владельца. P1: локальная блокировка биометрией, уведомления о новых входах, настройка показа содержимого уведомлений на заблокированном экране.

Общие настройки темы, размера текста, сроков, остатка и расписания уже реализованы. Тема и размер текста при реальной синхронизации должны иметь приоритет устройства; медицинские напоминания учитывают часовой пояс и правила поездок. Пока уведомления только внутри приложения. Маркетинговые рассылки и аналитика не включаются вместе со входом; при необходимости это отдельные необязательные настройки с самостоятельным основанием.

## Требования РФ и решения до запуска

Это техническая карта требований; финальные формы и применимость исключений зависят от оператора, договоров и реальных потоков данных.

- **Авторизация.** Для сервиса российского владельца, работающего в интернете на территории РФ, ч. 10 ст. 8 149-ФЗ ограничивает способы авторизации пользователей в РФ. Проект использует собственную систему российского оператора и Яндекс после проверки соответствия. Google отключён в RU-политике на сервере, а не только скрыт в UI. Собственная авторизация по email не равна авторизации через Google. Доставка письма иностранному почтовому провайдеру всё равно требует оценки передачи данных. [149-ФЗ, ст. 8](https://www.consultant.ru/document/cons_doc_LAW_61798/78b773a28f3ad19eb234697b20ab1d48c09f748a/).
- **Локализация.** Первичное собирание и связанные операции с ПД граждан РФ должны соответствовать ч. 5 ст. 18. Планируем БД, резервные копии, очереди, журналы и мониторинг с ПД в РФ; иностранная аналитика и error tracking с идентификаторами по умолчанию выключены. Реплика в РФ поверх исходной иностранной БД не решает требование. [152-ФЗ, ст. 18](https://www.consultant.ru/document/cons_doc_LAW_61801/cbf4e15b7c330f9372e876cdf2bc928bad7950ef/).
- **Здоровье.** Лекарства и история приёма могут раскрывать здоровье — это консервативная проектная оценка. Для таких сведений учитывается ст. 10: требуется допустимое основание, в том числе письменное согласие, если выбран именно этот путь. Нельзя заменить его общей галочкой регистрации. [152-ФЗ, ст. 10](https://www.consultant.ru/document/cons_doc_LAW_61801/26edb2934b899bf9c74c3a8f7e574651c6565e6d/).
- **Согласия.** Согласие оформляется отдельно от иных подтверждаемых документов. Если нужна письменная форма, электронный эквивалент требует допустимой электронной подписи и выполнения требований к содержанию. SMS/email OTP для входа сам по себе не означает выполнение этих требований. Храним версию документа, конкретный состав данных и целей, способ подписания, доказательство, дату и отзыв; облако включается только по проверенному сервером основанию. [152-ФЗ, ст. 9](https://www.consultant.ru/document/cons_doc_LAW_61801/6c94959bc017ac80140621762d2ac59f6006b08c/).
- **Роскомнадзор.** До обработки определяем необходимость уведомления оператора по ст. 22. Для трансграничной передачи предусмотрено отдельное предварительное уведомление и оценка получателя; выбор отечественного SMTP не гарантирует отсутствие передачи при отправке на зарубежную почту. Реальный список доменов снимается с allowlist только после этой оценки. [Ст. 22](https://www.consultant.ru/document/cons_doc_LAW_61801/d996966e22e1320c9de1ab82d9f6be12c3d9d765/), [ст. 12](https://www.consultant.ru/document/cons_doc_LAW_61801/e4ebbe1780de623c7cf32a59ca82a7bb523a25dd/).
- **Оператор и безопасность.** Утверждаем реквизиты оператора, политику, договоры обработки с подрядчиками, цели и сроки хранения, процедуру запросов, уничтожения и реагирования на инциденты; определяем применимость ПП РФ №1119 и требований ФСТЭК №21, модель угроз и требуемые меры. Логи не должны содержать пароли, OTP, OAuth-коды, токены или названия препаратов. Отзыв основания останавливает дальнейшую обработку соответствующих данных; сроки удаления, законные исключения и судьба резервных копий описываются в действующей политике.

Самостоятельный аккаунт без облачных медицинских данных должен оставаться доступным. Отказ от необязательной аналитики или маркетинга не закрывает доступ к аптечке. Текст «всё соответствует РФ» до выполнения этих действий показывать нельзя.

При инциденте из ч. 3.1 ст. 21 предусмотрены уведомление уполномоченного органа в течение 24 часов и сообщение результатов внутреннего расследования в течение 72 часов. Для отзыва согласия и достижения цели ст. 21 предусматривает правила прекращения обработки и уничтожения, включая срок до 30 дней при указанных в ней условиях и исключениях. Это нужно включить в процессы оператора, задания удаления и политику резервных копий; нельзя обещать бесконечное хранение удалённого аккаунта в бэкапах. [152-ФЗ, ст. 21](https://www.consultant.ru/document/cons_doc_LAW_61801/d3fe43a7c415353b17faab255bc0de92bea127da/). Меры безопасности выбираются по уровню защищённости и угрозам, а не по наличию одной функции шифрования; см. [состав мер ФСТЭК №21](https://www.consultant.ru/document/cons_doc_LAW_146520/a6615f7b0ffcc68aa0e0796336836d16febbfb4b/).

## План подключения настоящего сервиса

1. Определить российского оператора, выбрать площадку/БД/резервные копии в РФ и договоры. Уточнить правовую модель данных о здоровье и общего доступа.
2. Подготовить уведомления и действующие документы, определить сроки хранения и подписываемую форму, реализовать проверку доказательства на сервере.
3. Перенести dev-ядро в production framework и PostgreSQL. Добавить централизованные лимиты, мониторинг, TLS, Secure cookie, управление секретами, ротацию ключей, фоновые удаления, аудит без медицинского содержимого и проверки прав для каждого объекта.
4. Зарегистрировать Яндекс-приложение с минимальным `login:info`, настроить callback и российскую доставку писем. Проверить iOS-решение по [App Store 4.8](https://developer.apple.com/app-store/review/guidelines/#login-services). При необходимости выполнить отдельную интеграцию VK.
5. Подключить Flutter через системный браузер и защищённое хранение сессий; заменить локальный контроллер аккаунтов сетевым. Демо не преобразуется в настоящий аккаунт автоматически.
6. Реализовать и проверить миграцию гостя, синхронизацию, права, приглашения, отзыв, экспорт и удаление, восстановление из резервных копий и отказоустойчивость. Облако включить после выполнения предыдущих пунктов.

Протокол Яндекса: [PKCE и запрос авторизации](https://www.yandex.ru/dev/id/doc/ru/codes/code-url), [проверка идентификатора и client_id](https://yandex.ru/dev/id/doc/ru/user-information). Ориентиры безопасности: [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html).
